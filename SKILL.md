# Сборка документации компонента в Figma

Вход — ссылка на сам продуктовый компонент. Выход — SECTION с шестью страницами, собранными из компонентов движка `ds-*`. Ничего не рисуется с нуля: паттерны инстанцируются и заполняются.

**Модель распространения.** Движок — Figma-файл, который пользователь копирует к себе или подключает как библиотеку. Скилл переносимый и работает в любом файле, где движок доступен: он находит `ds-*` по имени, не по id. Весь визуал документации задаётся локальными переменными коллекции `decoration` — пользователь меняет там типографику, цвета, акценты, радиусы, отступы, и документация перерисовывается целиком. Скилл в эту механику не вмешивается.

## Обязательный контекст

| Файл | Когда читать |
|---|---|
| `references/ds-engine-map.md` | до первого действия — все `ds-*`, node-id, keys, property |
| `references/build-recipes.md` | до первого действия — сниппеты Plugin API |
| `references/interview.md` | до шага 4 |
| `references/annotations.md` | до сборки «Спецификации» |
| `references/designers.md` | до интервью по «Истории изменений» |
| `references/contract-template.md` | только на шаге 7 при выгрузке в markdown |

Скилл `figma-use` — обязателен перед **каждым** вызовом `use_figma`.

**Проверка комплектности — шаг 0, до всего остального.** Прочитать все шесть файлов. Хотя бы один не читается — назвать, какого не хватает, и закончить. Не восстанавливать содержимое чтением Figma-файла, не работать «по памяти», не собирать на том, что есть: без карты движка и рецептов результат будет разный от запуска к запуску, а пользователь этого не заметит. Отсутствие референсов почти всегда значит, что скилл установлен неправильно — распакован без папки `references/`.

## Незыблемые правила

1. **Вход — только сам компонент.** `COMPONENT_SET` или `COMPONENT`. Инстанс, фрейм, секция, группа → стоп (шаг 1).
2. **Исходный компонент не трогать.** Свойства, слои, имя, описание — только чтение. Исключение: перенос самого set в `Slot Component` (6.3) по прямому решению владельца.
3. **Шапку не трогать.** `Title` = название раздела, `Description` = его подзаголовок; оба привязаны к переменным коллекции `decoration`. Имя компонента в шапку не подставлять. Любой `setProps` по ним рвёт связь с переменной.
4. **Чисел в тексте нет.** Размеры, отступы, радиусы, цвета, типографика → аннотации с `properties` и линейки. См. `annotations.md`.
5. **Визуал не задавать значениями.** Никаких `fills`, `fontSize`, `fontName`, `cornerRadius`, `strokeWeight` числом на созданных узлах: всё приходит из движка через переменные коллекции `decoration`, заданное вручную перебивает тему. Геометрию (отступы, шаг блоков) копировать с соседних узлов движка. В `decoration` не писать. Исключение — SECTION документации: её скилл создаёт сам и обязан оформить, но **только привязкой к переменным**, не значениями (5.1).
6. **Писать только внутрь своей SECTION.**
7. **Не выдумывать содержание.** Варианты, состояния, анатомия — из компонента. Смысл, рекомендации, микрокопирайт — от пользователя. Пустой блок лучше выдумки.
8. **Инкрементально.** Одна страница — один вызов `use_figma`, после каждой `get_screenshot`.
9. **Возвращать ID** всех созданных узлов.
10. **Без подтверждения плана (шаг 3) не писать.**

## Пайплайн

### 1. Разобрать ссылку, проверить вход

`fileKey` и `node-id` из URL (дефис между числами → двоеточие). Без `node-id` — запросить.

| Вход | Действие |
|---|---|
| `COMPONENT_SET` | работать с ним |
| `COMPONENT` без родителя-set | работать с ним; на `Components` не будет подписей осей |
| `COMPONENT` внутри set | подняться к родителю, без вопроса |
| `INSTANCE`, `FRAME`, `SECTION`, `GROUP`, прочее | **стоп** |

Стоп = ничего не создавать, внутрь узла не лезть, не угадывать. Назвать тип и имя пришедшего узла, сказать, что нужна ссылка на сам компонент, закончить. Продолжение — только с новой ссылкой.

Причина: тот же узел позже ложится в `Slot Component` (6.3). Из инстанса или фрейма его туда не положить.

### 2. Инвентарь (read-only, рецепт 1)

Снять: имя, `key`, `description`, `documentationLinks`; `componentPropertyDefinitions`; фактические комбинации вариантов (не декартово произведение); дерево слоёв `defaultVariant` до глубины 3; вложенные инстансы; токены через `get_variable_defs`.

**Порядок свойств сохранить дословно** — в нём пойдут блоки спецификации (6.2). Не сортировать.

**Имена — дословно, включая опечатки.** Имя компонента, значения VARIANT и имена слоёв переносятся в документацию как есть. Расхождение между документацией и исходником хуже опечатки: по имени идёт поиск и сверка. Замеченные опечатки перечислить в отчёте отдельным пунктом — это находка для владельца, а не повод править текст.

**`description` компонента — черновик лида.** Если он не пуст, показать его **дословно** на шаге 4 и спросить, брать так или пользователь напишет свой. Грамматику и формулировки самому не чинить: показанный текст должен совпадать с тем, что лежит в компоненте, иначе непонятно, что подтверждают.

### 3. Согласовать план

```
Компонент:        <имя> (<N> вариантов, оси: <Ось=знач|знач>, …)
Куда:             страница <имя>, новая секция «<имя компонента>»
Страницы:         <какие собираем>
Блоки спеки:      <по свойствам, в порядке объявления>
Версия changelog: <посчитана по типу изменения>
Страница компонента: один блок «<имя>», ось X — <ось>, уровни Y — <ось / ось / ось>
```

Спросить: какие страницы собирать, какая ось в столбцы, как вкладываются уровни вертикальной оси. Дождаться подтверждения. Пустые страницы молча не создавать.

Если инвентарь показывает, что странице нечем наполниться, **предложить её пропустить прямо в плане, с причиной**. Признаки: нет оси состояний и нет прототипных связей → `interation` соберётся пустой; единственное текстовое свойство и нет ограничений → `microcopy` не о чем. Это предложение, а не решение: пропуск подтверждает пользователь.

### 4. Интервью

По `interview.md`. ≤5 вопросов за подход. Не спрашивать снятое на шаге 2.

| Паттерн | Обязательный вход |
|---|---|
| `changelog` | тип (New/Changed/Fixed), описание, участники |
| `specification` | лид; назначение каждого слоя анатомии; заголовок и описание на каждое свойство; где показывать описания строк |
| `interation` | триггер → реакция; motion-токены |
| `tips-practices` | пары «делать / не делать» |
| `microcopy` | правила текста по слотам |
| `components` | ничего — из шага 2 |

Шапка во входе не нуждается: она из движка.

### 5. Разрешить движок и подготовить площадку (рецепты 2, 2а)

Сначала найти движок. Порядок: по имени в текущем файле → по `key` через `importComponentByKeyAsync`, если подключён как библиотека → по node-id как быстрый путь в файле-первоисточнике. Разрешённые узлы держать в памяти сборки.

Совпадение по имени **точное**, включая опечатки движка. Похожие имена не подбирать, замену не подставлять. Не нашлось — остановиться и вернуть три списка: что ожидалось, что найдено, чего не хватает, плюс вероятную причину (переименованы компоненты движка или движок не подключён).

Затем один вызов: `setCurrentPageAsync` (ровно раз) → загрузить шрифты, снятые с узлов движка, а не захардкоженные → `SECTION` с именем компонента справа от самого правого узла → оформить её (5.1).

#### 5.1 Оформление SECTION

Секция — часть визуальной системы, а не голый контейнер. Оформляется привязкой к переменным `decoration`:

| Свойство | Переменная | Константа движка |
|---|---|---|
| радиус, все четыре угла | `radius/ds-radius-section` | — |
| заливка нижняя | `color/section/ds-section-02` | opacity 1 |
| заливка поверх | `color/section/ds-section-01` | opacity 0.01 |
| обводка | `color/ds-tertiary` | opacity 0.4, weight 1, align `INSIDE` |

Цвета и радиус — **только `setBoundVariable` и `setBoundVariableForPaint`**, значениями не писать. Прозрачности, толщина и выравнивание обводки переменными не покрыты — это константы движка.

Переменной нет в коллекции — остановиться и назвать какой, а не подставлять цвет руками.

Если в файле уже есть готовая секция документации, снять настройки с неё: так правки владельца подхватятся сами.

Раскладка: отступ от края секции 100 по всем сторонам, страницы слева направо в порядке сборки с шагом 200.

### 6. Страницы — по одной за вызов

Инстанс паттерна → `detachInstance()` → заполнить `Content`. Детач обязателен: у паттернов нет публичных property, а число блоков заранее неизвестно. `Header` после детача остаётся инстансом `ds-doc-header` — не трогать.

| Паттерн | Наполнение |
|---|---|
| `ds-doc/changelog` | N × `ds-log` — см. 6.1 |
| `ds-doc/specification` | лид + анатомия + блок на свойство — см. 6.2 |
| `ds-doc/interation` | `ds-doc-component Type=Device`, инстанс в `Slot Device` |
| `ds-doc/tips-practices` | пара блоков на правило |
| `ds-doc/microcopy` | `ds-paragraph-ux-wtiting` + блоки `Type=Structure` |
| `ds-doc/components` | один блок `Name Component` — см. 6.3 |

**Имя frame берётся из `Title` шапки этой же страницы.** После детача прочитать `Title` у инстанса `ds-doc-header` и присвоить его `frame.name`. Своих названий не придумывать и списком не хардкодить: `Title` привязан к переменным `decoration`, поэтому имена frame'ов идут за темой и языком библиотеки. В файле-первоисточнике это даёт `Changelog`, `Specification`, `Animated`, `Tips and practices`, `Microcopy`, `Components`.

`Title` пуст — взять имя паттерна без префикса `ds-doc/`.

Имя — снимок на момент сборки: если пользователь потом поменяет значение переменной, frame сам не переименуется. При пересборке подтянется новое.

После каждой страницы — `get_screenshot`, раскладку чинить сразу.

#### 6.1 `ds-doc/changelog`

Только записи `ds-log`. Одна запись = одно изменение. Свежая первой сверху (`insertChild(0, …)`).

Версия не спрашивается — считается из типа:

| `Type` | Значение | Версия |
|---|---|---|
| `New` | новая версия компонента | `Major+1`, `Minor=0`, `Patch=0` |
| `Changed` | доработка | `Minor+1`, `Patch=0` |
| `Fixed` | исправление | `Patch+1` |

База — версия верхней записи. Первая запись компонента всегда `1.0.0` / `New`. Посчитанное показать в плане (шаг 3).

- **Дата** — сегодняшняя. Отдельно спрашивать только при записи задним числом. Ведущие нули обязательны (`01`, не `1`), год двузначный.
- **Описание** — от пользователя, обязательно, `Show Description = true`. Нет описания → страницу не собирать, вынести в отчёт как пробел.
- **Дизайнеры** — слот принимает сколько угодно инстансов `ds-log-designers`, один на человека, порядок как назвал пользователь. Спрашивать всегда, имена подсказывать из `designers.md`, новое имя дописать туда после сборки.
- **Файлы и аватарки** — `Show File = false`, слот `File` не заполнять, `✱ Image` не менять. Осознанное решение, в отчёт как пробел не выносить.

#### 6.2 `ds-doc/specification`

**Лид** — `ds-paragraph` напрямую в `Content`, не в `Group`. `Show Title = false`, только `Description`: имя компонента жирным, дальше что это и когда брать, 1–2 предложения.

**Анатомия** — `Group`: `ds-paragraph H1` (`Title` = «Анатомия», `Description` = «Для ознакомления структурой компонента используйте DevMode (Shift+D)») + по одному `ds-doc-component Type=Structure` на конфигурацию, `Title` = имя конфигурации, `Show Desciption = false`, в `Slot Structure` — инстанс варианта.

Детали — аннотациями на слоях внутри инстанса: назначение в `labelMarkdown`, значения в `properties`. Каждый layout размечен. При нескольких конфигурациях аннотации **не дублировать**: первая несёт общую архитектуру, каждая следующая — только отличия. См. `annotations.md`.

**Дальше — по блоку на свойство, в порядке `componentPropertyDefinitions`.** Блок = `Group` из двух узлов:

1. `ds-paragraph Type=H1` — `Title` по-русски, `Description` = что задаёт свойство;
2. `ds-doc-component Type=State`, `Show Title = false`, `Show Desciption = false`; в `Slot State` — по `ds-doc-component-state` на каждое значение.

Описания строк включать там, где значение неочевидно (конфигурации, стили, размеры), выключать где имя самодостаточно (состояния). Решает пользователь.

Исключения: `Selected` — строка внутри блока «Состояния», не отдельный блок. Булево свойство становится блоком, если у него своя логика показа; в описании указать, при каких значениях других осей оно доступно.

Размеры — линейкой `addMeasurement`. Стили — аннотацией `properties: ["fills"]` на превью.

#### 6.3 `ds-doc/components`

**Один блок `Name Component` на компонент.** Дробить на блоки под пары осей — ошибка. Семейство из нескольких set именуется через слэш (`<Сущность> / <Роль>` — например одиночный элемент и группа), блок на каждый, внутри блока по-прежнему один фрейм.

| Узел | Содержимое |
|---|---|
| `Name` | `Name Component#10010:1` = имя компонента; `ds-log-changelog-version` = текущая версия |
| `Slot Component` | **один узел** — сам компонент со всеми вариантами в штатной раскладке |
| `Horizontal Props` | `Line[0]` = имя оси (`Large=True`), `Line[1]` = значения |
| `Vertical Props` | по `Line` на уровень вложенности; внутренний уровень — фрейм с `Line` на блок строк |

Уровни: `Vertical=True` у всех; крупный — `Large=True`, вспомогательный — `Large=False`. Иерархия читается по высоте скобки: подпись, накрывающая две другие, — их родитель. Верхний уровень может не быть осью компонента — например режим темы `Light` / `Dark`.

Подписи — дословные значения VARIANT. Порядок колонок уровней задаёт владелец; скилл повторяет фактическую раскладку компонента.

### 7. Обтянуть секцию, отчёт и выгрузка

**Обтяжка — последним шагом**, когда все страницы собраны и высоты окончательные: размер секции = габариты содержимого плюс отступ 100 с каждой стороны, через `resizeWithoutConstraints`. `SECTION` не умеет auto-layout и сам не хугает.

Отчёт: ссылка на секцию, собранные страницы, число блоков и вариантов, что осталось незаполненным.

По запросу — markdown-контракт по `contract-template.md`, чтением уже построенных страниц. Обратный проход: проверяет, что собранное читается однозначно.

## Чек-лист

1. `componentPropertyDefinitions` исходника совпадают до и после.
2. Всё внутри одной SECTION, снаружи ничего.
3. Шапки не тронуты, привязка к переменным `decoration` цела, имени компонента в них нет. Имя каждого frame совпадает с `Title` его шапки.
4. Ни на одном созданном узле не задан визуал вручную; в коллекцию `decoration` ничего не записано.
5. В текстах нет чисел.
6. Аннотации на каждом layout анатомии, у каждой заполнены `properties` и категория; между конфигурациями не дублируются.
7. Блоки спецификации идут в порядке свойств компонента.
8. Страница `ds-doc/components` — один блок, в `Slot Component` один узел.
9. Подписи осей дословные; вложенность уровней повторяет раскладку компонента.
10. Changelog: версия посчитана по типу, дата с ведущими нулями, в `Designers` столько инстансов, сколько названо, `Show File` = `false`.
11. Скриншот каждой страницы просмотрен, переполнений и наложений нет.
12. Незаполненное перечислено в отчёте, а не замаскировано плейсхолдером.
13. Имена компонента, вариантов и слоёв перенесены дословно; замеченные опечатки вынесены в отчёт отдельным пунктом.
14. SECTION оформлена: радиус, две заливки и обводка привязаны к переменным `decoration`, ни один цвет не задан значением.
15. SECTION обтянута по содержимому: отступ 100 со всех сторон, пустого места за последней страницей нет.
