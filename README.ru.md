# Component Spec Kit

[English version →](README.md)

Движок документации дизайн-системы в Figma и два скилла Claude Code, которые с ним работают: **`spec-kit-docs`** собирает документацию, **`spec-kit-theme`** её перекрашивает.

Документация компонента — это секция в Figma из трёх страниц: `Changelog`, `Specification`, `Components`. Без них документации не бывает, и ровно их собирает скилл. Страницы не рисуются с нуля: они собираются из готовых паттернов `ds-doc/*`, а весь визуал приходит из переменных коллекции `theme`. Поменяли токен — перерисовалась вся документация сразу.

В движке есть ещё один паттерн — `Interaction`. Скилл его не создаёт: то, что там пишут, нельзя вывести из компонента. Соберите его вручную из библиотеки, когда будет что сказать.

Собрать секцию можно руками. Скилл делает то же самое, только быстрее и не забывает правила.

Второй скилл работает уровнем ниже. Весь визуал документации приходит из коллекции переменных `theme`, а мод этой коллекции — и есть тема. `spec-kit-theme` читает картинку-референс, разворачивает её в 164 переменных и записывает отдельным модом: та же документация показывается в другой шкуре, и ни одна страница при этом не трогается.

**Это дизайн-представление компонента, а не руководство по реализации для разработчиков.**

- **Начать отсюда:** [OVERVIEW.md](OVERVIEW.md) — что с чем работает, какой файл брать к какому репозиторию
- **Репозиторий:** [github.com/jsr993/component-spec-kit](https://github.com/jsr993/component-spec-kit)
- **Figma-файл движка:** [Component Spec Kit в Figma Community](https://www.figma.com/community/file/1666170620013431022/component-spec-kit) — скопируйте его себе
- **Готовые архивы скиллов:** [`dist/spec-kit-docs.skill`](dist/spec-kit-docs.skill), [`dist/spec-kit-theme.skill`](dist/spec-kit-theme.skill)
- **Как всё устроено внутри:** [ARCHITECTURE.md](ARCHITECTURE.md) — для тех, кто развивает движок и скилл

> `spec-kit-docs` один на оба языка: **язык документации следует за языком запроса**. Написали по-русски — содержание блоков будет русским, по-английски — английским. Заголовки разделов приходят из переменных Figma-файла и следуют его языку.

## Часть 1. Как работать с документацией в Figma

### Подготовка файла

1. Скопируйте файл движка себе в проект.
2. Измените токены коллекции **Local Variables → `theme`** под свою дизайн-систему: цвета, отступы, радиусы, типографику.
3. Опубликуйте файл и подключите его как библиотеку — либо собирайте документацию прямо в копии.

**При публикации проверьте, что переменные ушли вместе с компонентами.** Коллекция `theme` должна попасть в публикацию: если она скрыта от неё (`Hide from publishing`) или план Figma не поддерживает публикацию переменных, компоненты будут импортироваться нормально, а сборка остановится на оформлении секции — скиллу будет не к чему привязаться. Симптом ровно такой: страницы собираются, секция — нет. Проверить можно до сборки: в файле-потребителе откройте `Libraries` — у библиотеки движка должны значиться и components, и variables.

Скилл ищет компоненты движка **по имени**, а не по id, поэтому работает в любой копии файла. Имена движка — часть контракта: переименовывать `ds-*` нельзя, включая опечатки в них (`ds-doc/interation`, `Show Desciption#757:0`).

### Как устроена секция

Имена страниц скилл не придумывает и не хранит списком — он берёт их из `Title` шапки, а тот привязан к переменной `theme`. Поэтому имена идут за темой и языком файла; ниже — то, что получается в файле-первоисточнике.

| Страница | Паттерн | Про что |
|---|---|---|
| `Changelog` | `ds-doc/changelog` | версия, тип изменения, дата, авторы |
| `Specification` | `ds-doc/specification` | лид, анатомия, блок на каждую ось |
| `Components` | `ds-doc/components` | сам component set с подписями осей |
| `Interaction` | `ds-doc/interation` | триггер → реакция, motion-токены — **вручную** |

Порядок сборки страницы: инстанс паттерна → `Detach` → наполнить `Content` атомами `ds-doc/specification/paragraph` и `ds-doc/specification/component`. Детач нужен потому, что число блоков заранее неизвестно, а публичных свойств у паттернов нет. **Шапка внутри страницы остаётся инстансом `ds-doc/header`** — её трогать не нужно.

Все страницы одного компонента складываются в одну секцию слева направо, отступ от края 100, шаг между страницами 200. Секция не умеет auto-layout — обтягивайте её вручную последним шагом.

### Правила оформления

1. **Шапку не трогать.** `Title` — это название раздела (`Changelog`, `Specification`, `Components`), а не имя компонента. Все три текста шапки привязаны к переменным `theme`; любая перезапись рвёт связь.
2. **Чисел в тексте нет.** Размеры, отступы, радиусы, цвета и типографику показывайте аннотациями Figma (с заполненным `properties`) и линейками `addMeasurement`. Тогда значения обновляются вслед за компонентом, а документацию не переписывают — в неё только добавляют и из неё убирают блоки.
3. **Визуал не задавать значениями.** Никаких `fills`, `fontSize`, `cornerRadius` числом. Только привязка к переменным `theme` — иначе блок выпадет из темы. В саму коллекцию `theme` скилл не пишет.
4. **Порядок блоков «Спецификации» = порядок свойств компонента.** Не сортировать, не перегруппировывать.
5. **Анатомия — про архитектуру, а не про картинку.** Блок на каждую конфигурацию, аннотации только на отличия. Дублировать одинаковые аннотации на всех блоках — ошибка.
6. **Страница «Компоненты» — один блок на компонент.** В `Slot Component` кладётся сам component set целиком, а не набор инстансов. Семейство из нескольких set именуется через слэш: `Chips / Item`.
7. **Факты не выдумываются.** Варианты, состояния, анатомия и порядок свойств берутся из компонента. Заголовки и описания скилл пишет по шаблонам и перечисляет их в отчёте. Смысл, который из компонента не выводится, остаётся пустым: пустой блок лучше правдоподобной выдумки. Это назначение конфигураций, разница стилей, правила текста и рекомендации.
8. **Имена переносятся дословно**, включая опечатки исходника: по имени идёт поиск и сверка. Замеченные опечатки выносятся в отчёт, а не правятся в тексте документации.

### Категории аннотаций

Пресеты аннотаций в файле: **Development** (green), **Interaction** (blue), **Accessibility** (pink), **Content** (orange).

## Часть 2. Скилл `spec-kit-docs` — собирает документацию

Скилл читает компонент, снимает инвентарь вариантов и свойств и строит секцию из трёх паттернов `ds-doc`. Исходный компонент он только читает.

**Работает автономно.** От ссылки до готовой секции — **ни одного подтверждения**: ни плана, ни интервью, ни вопроса перед записью. Это сделано под поточную задачу: задокументировать подряд десятки компонентов, а не один. Скилл останавливается только там, откуда идти некуда: нет библиотеки, на входе не компонент, не нашлась переменная движка, не читаются референсы. Остановка — тупик, а не контрольная точка.

### Что понадобится

- **Claude Code** — клиент Claude, который работает в терминале.
- **Figma MCP** с правом записи в файл (write to canvas).
- Файл, в котором доступен движок `ds-*`: ваша копия или подключённая библиотека.

Библиотеку скилл проверяет нулевым шагом и опознаёт её **по коллекции переменных `theme`**, а не по имени. Поэтому своя копия, опубликованная под своим названием, работает наравне с оригиналом; имя «Component Spec Kit» — только значение по умолчанию. Нет ни библиотеки, ни локальных `ds-*` — скилл останавливается и просит подключить. Из кода библиотеку не подключить, Plugin API этого не умеет.

### Установка скилла

1. Скачайте архив. В `dist/` лежит одна и та же сборка в двух формах — выбирайте по способу установки:

   | Файл | Что внутри | Когда брать |
   |---|---|---|
   | [`spec-kit-docs.skill`](dist/spec-kit-docs.skill) | `SKILL.md` и `references/` в корне | распаковываете руками **внутрь** `~/.claude/skills/spec-kit-docs/` |
   | [`spec-kit-docs.zip`](dist/spec-kit-docs.zip) | всё обёрнуто в папку `spec-kit-docs/` | загружаете через форму или распаковываете «куда попало» — папка приезжает вместе с архивом |

   У каждой формы есть двойник с версией в имени (`spec-kit-docs-6.0.0.skill`, `spec-kit-docs-6.0.0.zip`), чтобы сборка на диске опознавалась не открываясь. **В `dist/` лежит только текущая версия** — прошлые сборка удаляет, за историей в git. `spec-kit-theme` приезжает теми же четырьмя формами под своим именем.
2. **Сначала удалите старую папку.** Поверх не распаковывайте: состав референсов между поколениями меняется, и лишний файл заставит новый `SKILL.md` считать папку полной.

   ```bash
   rm -rf ~/.claude/skills/spec-kit-docs
   ```

   Если вы приехали с версии 5 или раньше, установленная папка ещё называется прежним именем скилла. Удалите и её — иначе Claude Code покажет обе и запустит ту, что совпала первой:

   ```bash
   rm -rf ~/.claude/skills/ds-doc-build
   ```

3. Распакуйте архив в папку скиллов:

   ```
   macOS / Linux   ~/.claude/skills/spec-kit-docs/
   Windows         %USERPROFILE%\.claude\skills\spec-kit-docs\
   ```

   Путь важен: Claude Code показывает в списке скиллов только те папки, где **прямо внутри лежит `SKILL.md`** с frontmatter. Файлы уровнем глубже — скилла в списке не будет, и ошибки тоже.

4. Проверьте структуру — должно получиться так:

   ```
   spec-kit-docs/
   ├── SKILL.md
   └── references/
       ├── ds-engine-map.md
       ├── build-recipes.md
       ├── annotations.md
       ├── contract-template.md
       └── locales/
           ├── en.md
           └── ru.md
   ```

   **Без папки `references` скилл откажется работать.** Он проверяет комплектность нулевым шагом и останавливается, если хотя бы один файл не читается: без карты движка и рецептов результат был бы разным от запуска к запуску, а вы бы этого не заметили.

5. Claude Code подхватывает изменения в папке скиллов на лету. Перезапуск нужен, только если папки `skills` раньше не существовало.

Альтернатива архиву — клонировать репозиторий и положить симлинк:

```bash
git clone https://github.com/jsr993/component-spec-kit.git ~/src/component-spec-kit
ln -s ~/src/component-spec-kit/skills/spec-kit-docs  ~/.claude/skills/spec-kit-docs
ln -s ~/src/component-spec-kit/skills/spec-kit-theme ~/.claude/skills/spec-kit-theme
```

Оба скилла лежат рядом в `skills/`, так что один клон покрывает пару, а `git pull` обновляет их вместе.

### Если ставите впервые

1. Установите Claude Code и войдите в аккаунт Claude.
2. Подключите Figma MCP:

   ```bash
   claude mcp add --scope user --transport http figma https://mcp.figma.com/mcp
   ```

3. В Claude Code введите `/mcp`, выберите `figma` и авторизуйтесь. Figma спросит разрешение на запись в файлы — его нужно дать, иначе скилл сможет только читать.
4. Дальше — установка скилла из пункта выше.

### Как запускать

Пришлите ссылку на **сам компонент** — `COMPONENT` или `COMPONENT_SET`:

```
Собери документацию по компоненту
https://www.figma.com/design/<fileKey>/<file>?node-id=3014-2258
```

Ссылка на инстанс, фрейм, секцию или группу не подойдёт: скилл назовёт тип узла, попросит ссылку на компонент и остановится. Тот же узел позже кладётся в `Slot Component`, а инстанс туда не положить.

Дальше вмешиваться не нужно. Скилл отчитается инвентарём: сколько вариантов, какие оси, в каком порядке пойдут блоки. Потом соберёт три страницы, показывая снимок после каждой.

Можно вызвать скилл и напрямую: `/spec-kit-docs`.

### Где он всё-таки остановится

Остановок ровно четыре, и каждая — тупик, а не контрольная точка:

- не читаются файлы `references/` — скилл распакован не полностью;
- в файле нет ни библиотеки, ни локальных `ds-*`;
- на входе не компонент, а инстанс, фрейм, секция или группа;
- не нашёлся компонент движка или переменная `theme`.

Во всём остальном скилл выбирает сам и пишет, что выбрал. Это осознанный размен: в потоке из полусотни компонентов вопрос на каждом — это не аккуратность, а остановка работы.

### Что он решает за вас

| Решение | Правило |
|---|---|
| версия и тип changelog | первая сборка — `1.0.0 / New`; пересборка — `New` → major+1, `Changed` → minor+1, `Fixed` → patch+1, по умолчанию `Changed` |
| дата | сегодняшняя |
| авторы | слот `Designers` не трогается — остаётся дефолт компонента |
| лид спецификации | непустой `description` компонента дословно, пустой — по шаблону |
| заголовки блоков | по глоссарию локали: `Configuration` → Конфигурации, `Style` → Стили, `Size` → Размеры, `State` → Состояния, остальные — как в компоненте |
| описания строк | включены для конфигураций, стилей и размеров; выключены для состояний |
| оси на `Components` | читаются из фактической раскладки сета: столбцы по кластерам `x`, вертикальные уровни по кластерам `y`, внешний первым |

Всё, что скилл написал сам, он перечисляет в отчёте отдельным списком. Это место, куда стоит заглянуть, — остальное проверяемо по компоненту.

### Чего скилл не делает

- Не меняет исходный компонент — свойства, слои, имя и описание только читает. Сет он переносит в `Slot Component`: у того меняются родитель и позиция на холсте, и больше ничего. Перенос называется в отчёте.
- Не пишет ничего за пределами своей секции.
- Не задаёт визуал значениями и не пишет в коллекцию `theme`.
- Не придумывает смысл: назначение конфигураций, разницу стилей, правила текста и рекомендации он оставит пустыми и перечислит в отчёте, а не замаскирует плейсхолдером.
- Не собирает `Interaction` — эта страница делается руками.

### Что на выходе

Секция в Figma и отчёт: ссылка на секцию, три страницы, число блоков и вариантов, список сгенерированных текстов, замеченные опечатки в именах исходника, перечень пробелов. По отдельному запросу скилл выгружает markdown-контракт — обратным проходом по уже построенным страницам, что заодно проверяет, читается ли собранное однозначно.

## Часть 3. Скилл `spec-kit-theme` — перекрашивает её

Всё, что видно в документации, — это переменная коллекции `theme`, а **мод** коллекции и есть тема. В файле их три: `lite`, `enterprise`, `engineering`. Переключили мод — перерисовались все когда-либо собранные страницы.

`spec-kit-theme` добавляет мод. Вы присылаете картинку понравившегося оформления — скриншот сайта, разворот гайдлайна, чужую документацию — и скилл записывает в `theme` новый столбец.

> Отчёт следует за языком запроса: спросили по-русски — бриф и сдача придут по-русски. В Figma скилл прозы не пишет, так что больше локализовать нечего.

### Как это устроено

Скилл **не читает** с картинки 164 значения. Модель, которой предложено назвать 164 числа, назовёт 164 правдоподобных, а правдоподобное — не согласованное: шкала перестаёт быть шкалой.

Вместо этого с картинки снимается **четырнадцать решений**: насколько светла подложка, чем отделены карточки, какие углы, какая плотность, какие гарнитуры несут заголовки и текст, где живёт акцент. Эти четырнадцать разворачиваются в полную коллекцию по фиксированным таблицам. Чего на картинке нет — наследуется из мода-образца и называется в отчёте наследованным, а не придумывается.

Перед брифом идёт выбор покрупнее: одна из **шести территорий** стиля, описанных в `references/style-space.md`. Это рамка, которая не даёт теме уехать в оформление, которое конструкция не вывезет.

### Как запускать

Приложите картинку и попросите тему:

```
Сделай тему по этому референсу
https://www.figma.com/design/<fileKey>/<file>
```

Скилл называет территорию и бриф целиком — у каждого решения помечено: прочитано с картинки, взято из территории или унаследовано, — затем разворачивает, проверяет и пишет. Читать стоит именно этот отчёт: это единственное место, где видно, что дал референс, а что решила развёртка.

### Чего он не делает

- **Не трогает существующие моды.** Любая запись в `lite` или `enterprise` — ошибка. Неудачная тема стоит одного удаления мода.
- **Не разрывает алиасы.** Семантический ярус остаётся алиасами на примитивы, как в образце: разорвёте — тема перестанет отвечать на правку примитива.
- **Не выдумывает гарнитуры.** Только Google Fonts, доступные в Figma, и только после проверки `listAvailableFontsAsync`; замены названы в отчёте.
- **Не перекраивает конструкцию.** Тексты разделов, ширина документа и мелочь `layer-03` копируются из образца дословно — они не тема.

Проверки идут до записи: контраст (`primary` ≥ 7:1, `secondary` ≥ 4.5:1), монотонность шкал, существование гарнитур. Проверка не прошла — правится бриф и разворачивается заново, а не пишется мод.

### Установка

Так же, как `spec-kit-docs`, под своим именем:

```
macOS / Linux   ~/.claude/skills/spec-kit-theme/
Windows         %USERPROFILE%\.claude\skills\spec-kit-theme\
```

```
spec-kit-theme/
├── SKILL.md
└── references/
    ├── theme-map.md        # коллекция: 164 переменных, два яруса, что не тема
    ├── token-usage.md      # какой токен чем управляет на холсте
    ├── style-space.md      # шесть территорий и то, чего конструкция не вывезет
    ├── expansion-rules.md  # четырнадцать решений и таблицы развёртки
    └── recipes.md          # Plugin API: addMode, setValueForMode, алиасы
```

Этот скилл тоже проверяет свою полноту и останавливается так же, если референс не читается.

## Структура репозитория

```
.
├── skills/
│   ├── spec-kit-docs/                # собирает документацию
│   │   ├── SKILL.md                  # пайплайн, правила, чек-лист
│   │   └── references/
│   │       ├── ds-engine-map.md      # карта движка: имена, node-id, keys, property
│   │       ├── build-recipes.md      # сниппеты Figma Plugin API
│   │       ├── annotations.md        # аннотации и линейки
│   │       ├── contract-template.md  # шаблон markdown-контракта
│   │       └── locales/              # строки, которые скилл пишет в документацию
│   │           ├── en.md
│   │           └── ru.md
│   └── spec-kit-theme/               # перекрашивает её
│       ├── SKILL.md
│       └── references/
│           ├── theme-map.md          # коллекция: 164 переменных, два яруса
│           ├── token-usage.md        # какой токен чем управляет на холсте
│           ├── style-space.md        # шесть территорий и то, чего не достать
│           ├── expansion-rules.md    # четырнадцать решений и развёртка
│           └── recipes.md            # Plugin API: addMode, setValueForMode, алиасы
├── dist/                             # по четыре архива на скилл, только текущая версия
│   ├── spec-kit-docs.skill           # плоский: SKILL.md в корне архива
│   ├── spec-kit-docs-6.0.0.skill     # он же, версия в имени
│   ├── spec-kit-docs.zip             # обёрнут в папку spec-kit-docs/
│   ├── spec-kit-docs-6.0.0.zip       # он же, версия в имени
│   └── spec-kit-theme.*              # те же четыре, под своим именем
├── scripts/
│   ├── pack.sh                       # пересобрать все архивы (macOS / Linux)
│   └── pack.ps1                      # пересобрать все архивы (Windows)
├── OVERVIEW.md                       # сквозной документ: половины и как их спарить
├── ARCHITECTURE.md                   # слои решения, локализация, версионирование
├── CHANGELOG.md
├── README.md                         # английская версия этого файла
└── README.ru.md
```

Добавить скилл — значит положить в `skills/` папку с `SKILL.md` и `references/` рядом: скрипты сборки обходят каталог и править их не нужно.

### Пересобрать архивы после правок

Один прогон пересобирает все скиллы из `skills/`:

```bash
./scripts/pack.sh          # macOS / Linux
powershell -File scripts/pack.ps1   # Windows
```
